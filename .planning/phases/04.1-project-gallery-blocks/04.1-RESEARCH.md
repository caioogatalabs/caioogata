# Phase 04.1: Project Gallery Blocks - Research

**Researched:** 2026-04-21
**Domain:** CSS Grid layout, scroll-linked animations, image composition patterns
**Confidence:** HIGH

## Summary

This phase rewrites the broken `ProjectGalleryStaggered` component and adds two new gallery section types (`gallery-full-bleed`, `gallery-stick`). The existing codebase already provides all the infrastructure needed: a 12-col Grid system, rAF-based scroll hooks (`useScrollReveal`, `useScrollExpand`), a sub-component pattern for hooks-in-loops (`RevealImage`), and a section-switch architecture in `ProjectPageShell`. The JSON data model (`GalleryRow` with `spans[]` and `images[]`) already contains the layout information that the staggered component currently ignores.

The primary technical challenge is the sticky gallery scroll driver (mapping scroll position to crossfade opacity across N slides), which follows the same rAF + ticking guard pattern established by `useScrollExpand`. The full-bleed component requires a CSS technique to break out of the padded parent container. Both are well-understood CSS patterns with no library dependencies.

**Primary recommendation:** Rewrite `ProjectGalleryStaggered` to render rows as CSS grid respecting `spans[]`, add `ProjectGalleryFullBleed` with 100vw bleed via `translateX(-50%)` technique, add `ProjectGalleryStick` with a new `useScrollStick` hook following the `useScrollExpand` architecture.

## Architecture Patterns

### Current Broken Pattern (What to Replace)

The current `ProjectGalleryStaggered` (line 91-118 of the file) flattens ALL images from ALL rows into a single array, then renders each image at 4/12 columns in a zigzag pattern using `STAGGER_COLS = [5, 9, 5, 1]`. This completely ignores the `spans[]` data in each `GalleryRow`.

```typescript
// BROKEN: flattens rows, ignores spans
const allItems = (section.rows || []).flatMap(row => row.images)
// Then renders each at fixed col-span-4 with zigzag position
```

### Pattern 1: Span-Aware Row Grid (GAL-01)

**What:** Each `GalleryRow` renders as its own 12-col CSS grid. Images fill columns according to their corresponding `spans[i]` value.

**Key implementation details:**
- Use raw CSS `grid-template-columns: repeat(12, 1fr)` per row (not the Grid component, which includes padding -- staggered section has its own padding wrapper)
- Map `spans[i]` to `grid-column: span N` using a static class map (same pattern as Grid.tsx DESKTOP_SPAN)
- Images use `object-cover` with `max-h-[500px]` and `min-h-[200px]` (from UI-SPEC)
- Gap: `gap-x-[4px] gap-y-[8px]` on the grid container

**Stagger animation:** Each image in a multi-image row needs its own `useScrollReveal` hook call (sub-component pattern). Add a `delay` parameter to `useScrollReveal` or handle stagger timing via CSS `transition-delay` on the clip-path. The existing `-a-N` stagger system uses 70ms intervals -- apply the same: image index 0 = 0ms, index 1 = 70ms, index 2 = 140ms.

**Responsive collapse (from UI-SPEC):**
- Mobile (<768px): all spans become col-span-12 (stack)
- Tablet (768-1023px): minimum 6-col per image
- Desktop (1024+): render spans as declared

```typescript
// Per-row rendering pattern
{section.rows?.map((row, rowIdx) => (
  <div key={rowIdx} className="grid grid-cols-12 gap-x-[4px]">
    {row.images.map((img, imgIdx) => (
      <StaggeredRevealMedia
        key={imgIdx}
        item={img}
        span={row.spans[imgIdx] || 12}
        staggerIndex={imgIdx}
      />
    ))}
  </div>
))}
```

### Pattern 2: Full-Bleed Layered Composition (GAL-02)

**What:** Background image bleeds 100vw edge-to-edge (breaking padded parent), with semi-transparent overlay and centered foreground image.

**100vw bleed technique:**
```css
/* Break out of padded parent */
width: 100vw;
position: relative;
left: 50%;
transform: translateX(-50%);
```

This is the standard CSS pattern for full-bleed elements inside constrained containers. It works because `left: 50%` moves the element to the center of the parent, then `translateX(-50%)` shifts it back by half its own width (which is now 100vw).

**DOM structure (from UI-SPEC):**
```
section.relative.py-24
  div.relative (100vw bleed container, left:50%, translateX:-50%)
    img.w-full.object-cover (background)
    div.absolute.inset-0.bg-bg (overlay, opacity: 0.6)
  div.relative.z-10.mx-auto (foreground, max-w-[66.666%])
    RevealImage (useScrollReveal wrapper)
      img.rounded-[12px] (foreground image)
```

**Data model:** Flat fields on `ProjectSection`:
```typescript
bgImage?: string     // background bleed image path
fgImage?: string     // foreground centered image path
bgAlt?: string       // background alt text
fgAlt?: string       // foreground alt text
```

### Pattern 3: Scroll-Pinned Sticky Gallery (GAL-03)

**What:** Container sized at `slideCount * 100vh`. Inside, a sticky element pins to viewport. Images crossfade based on scroll position.

**Architecture -- follows useScrollExpand pattern:**
1. Outer container: `position: relative; height: ${slideCount * 100}vh`
2. Inner sticky: `position: sticky; top: 0; height: 100vh; overflow: hidden`
3. All slide images stacked as `position: absolute; inset: 0` inside sticky
4. rAF scroll handler calculates which slide zone the user is in
5. Each slide gets `opacity` based on progress within its zone

**Scroll-to-opacity mapping (from UI-SPEC):**
- Total scroll range = container height - viewport height
- Each slide zone = total range / slideCount
- Within each zone: slide N opacity goes 1 -> 0 in last 20%, slide N+1 opacity goes 0 -> 1 in first 20%
- First slide starts at opacity 1, last slide ends at opacity 1

**New hook: useScrollStick**
```typescript
// Returns array of opacities, one per slide
function useScrollStick(slideCount: number): {
  containerRef: RefObject<HTMLElement>
  opacities: number[]
}
```

The hook follows the exact same pattern as `useScrollExpand`:
- `useRef` for the container element
- `useState` for the opacities array
- `useCallback` for the update function
- `useEffect` with scroll/resize listeners + rAF ticking guard
- `prefers-reduced-motion` check: if true, all opacities = 1 (stacked, no sticky)

**Mobile fallback (from UI-SPEC):** On mobile (<768px), no sticky behavior. Render as a vertical image stack with `position: relative` and `height: auto`.

### Anti-Patterns to Avoid
- **Hooks in loops:** Never call `useScrollReveal` inside `.map()`. Always use a sub-component (RevealImage pattern already established).
- **Dynamic Tailwind classes:** Never use template literals for grid spans (`col-span-${n}`). Use static class maps (same pattern as Grid.tsx).
- **overflow-hidden on bleed containers:** The full-bleed section must NOT have overflow-hidden -- it would clip the 100vw bleed.
- **Fixed image heights on staggered:** The old 340px fixed height is the core bug. Use max-height + object-cover for natural aspect ratios.

## Common Pitfalls

### Pitfall 1: Horizontal Scrollbar from 100vw
**What goes wrong:** `width: 100vw` includes scrollbar width on Windows/Linux, causing a horizontal scrollbar.
**Why it happens:** `100vw` = viewport width including scrollbar, but the body content area excludes it.
**How to avoid:** Add `overflow-x: hidden` on the section's nearest scrolling ancestor (the page body or the `.min-h-screen.bg-bg` wrapper in ProjectPageShell). Alternatively, use `width: 100%` on a full-width ancestor instead of `100vw`.
**Warning signs:** Horizontal scrollbar appears on pages with full-bleed sections.

### Pitfall 2: Stagger Delay with useScrollReveal
**What goes wrong:** All images in a row reveal simultaneously instead of staggering left-to-right.
**Why it happens:** `useScrollReveal` triggers based on element position in viewport, and all images in the same row are at the same Y position.
**How to avoid:** Add a `delay` mechanism. Options: (a) adjust `startFraction` per image to offset reveal start by ~70ms equivalent scroll distance, or (b) wrap each image's clip-path with a CSS `transition-delay` that creates the wave effect once reveal begins. Option (b) is simpler -- use a CSS transition on the clip-path value with staggered delay.
**Warning signs:** Multi-image rows all appear at once.

### Pitfall 3: Sticky Gallery Not Sticking
**What goes wrong:** The inner element scrolls normally instead of staying pinned.
**Why it happens:** Common causes: (a) parent has `overflow: hidden` or `overflow: auto`, (b) parent height is not tall enough, (c) sticky element height equals parent height.
**How to avoid:** Ensure the outer container is `position: relative` with explicit height (`slideCount * 100vh`). The sticky child must be shorter than its parent. No `overflow` property on any ancestor between the sticky element and the scrolling context.
**Warning signs:** Images just stack vertically with no pinning behavior.

### Pitfall 4: React State Thrashing on Scroll
**What goes wrong:** Excessive re-renders from updating opacity state on every scroll frame.
**Why it happens:** Setting state for N slide opacities on every rAF frame.
**How to avoid:** Use the same ticking guard pattern as existing hooks. Consider using `useRef` for opacity values and applying via `style` prop with direct DOM manipulation (ref.current.style.opacity) instead of React state, if performance is an issue. The existing hooks use `useState` successfully, so start with that.
**Warning signs:** Janky scroll performance on the sticky gallery, especially with 5+ slides.

### Pitfall 5: Span Mismatch Between spans[] and images[]
**What goes wrong:** If `spans.length !== images.length`, images don't align to grid or overflow.
**Why it happens:** Content authoring error in en.json.
**How to avoid:** Defensive code: if spans[i] is undefined, fall back to equal distribution (`12 / images.length` rounded). Log a dev warning.
**Warning signs:** Gallery looks broken on specific projects but not others.

### Scroll-Stick Opacity Calculation

```typescript
// Inside rAF update callback
const containerRect = containerRef.current.getBoundingClientRect()
const vh = window.innerHeight
const totalScroll = containerRect.height - vh
const scrolled = -containerRect.top // how far past the top
const progress = Math.max(0, Math.min(1, scrolled / totalScroll))

const newOpacities = slides.map((_, i) => {
  const slideStart = i / slideCount
  const slideEnd = (i + 1) / slideCount
  const crossfadeZone = 0.2 / slideCount // 20% overlap

  if (progress < slideStart - crossfadeZone) return 0
  if (progress > slideEnd + crossfadeZone) return 0
  if (progress >= slideStart && progress <= slideEnd) return 1

  // Fade in zone
  if (progress < slideStart) {
    return (progress - (slideStart - crossfadeZone)) / crossfadeZone
  }
  // Fade out zone
  return 1 - (progress - slideEnd) / crossfadeZone
})
```

## Open Questions

1. **Stagger delay mechanism**
   - What we know: Need 70ms per-image delay within a row for wave effect. `useScrollReveal` has no delay parameter.
   - What's unclear: Whether to modify `useScrollReveal` to accept a delay offset, or use CSS transition-delay on the clip-path value.
   - Recommendation: Use a `startOffset` parameter on `useScrollReveal` that shifts `startFraction` by a small amount per image index. This keeps the delay scroll-linked (not time-based) which feels more natural. Alternatively, the sub-component can simply adjust its own `startFraction` prop based on its index.

2. **Tablet responsive for staggered spans**
   - What we know: UI-SPEC says tablet minimum 6-col per image, so [4,4,4] becomes [6,6]+[12].
   - What's unclear: Whether to handle this in CSS (media query + grid overrides) or in JS (different span array per breakpoint).
   - Recommendation: CSS approach -- use `md:col-span-6` as minimum on tablet. For 3-image rows, the third image wraps to next row naturally in CSS grid. No JS breakpoint detection needed.
